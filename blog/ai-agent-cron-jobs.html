How to Run AI Agents on Cron Jobs (10 Real Examples With Costs)

Fernando Fernandez 8 min read 1,420 words
By Fernando Fernandez · runs 10+ AI cron jobs daily on a personal Linux server

The gap between "I have an AI agent" and "I have an AI agent that actually does things" is a cron job.

You can have the best memory system in the world, the best prompts, the best tool access. If you still have to open a terminal and start the thing every time, it's not doing much for you. Scheduling is what makes it useful.

Cron jobs are how you fix that. They're how your morning briefing shows up on your phone before you're out of bed. How your ticket queue gets reviewed without you touching it. How your Spanish practice lesson arrives whether you remembered to ask for it or not.

This post walks through the setup: job configurations, model choices, and what it actually costs to run.

What a Cron Job Actually Is

A cron job is a scheduled task. Your system runs it at the time you specify, whether you're there or not.

If you've set a recurring calendar reminder, you understand the mechanism. The difference is: instead of reminding you to do something, the agent goes and does it.

Syntax looks like this:

0 6 * * * /path/to/my-morning-briefing.sh

That runs at 7am every day. Five fields: minute, hour, day-of-month, month, day-of-week. Asterisk means "every." If you want to run something at 9am Monday through Friday only: 0 9 * * 1-5.

You set these up in a file called the crontab. Run crontab -e to edit it. That's it. Linux, macOS, WSL2, all support it.

What Makes a Good Cron Job Candidate

Not every task should be a cron job. The ones that work well share three characteristics:

A clear, bounded task. "Review tickets that haven't been touched in 48 hours and flag ones that need my attention" is good. "Do my work" is not. The job needs to know when it's done.

Output that goes somewhere useful. If the agent runs but you have no idea what it produced, you won't trust it. My cron jobs all deliver output to Telegram. I can see exactly what ran and what it decided.

No interactive clarification required. A cron job can't ask you a follow-up question. It needs enough context in its setup to handle the task without a back-and-forth. If a task normally takes five clarification questions before you can start, it's not a good cron job yet. Fix the prompts and context first.

My 10 Cron Jobs

Here are the main ones, with schedule and model assignment.

A note on cost: I run all of this on an Anthropic Max subscription ($100/month flat). No per-token billing. If you go the API route instead, per-run costs will depend on your model choices and context size, but for reference, Sonnet runs are typically pennies per call and even Opus stays under a dollar for most tasks. The subscription simplifies everything: I don't think about individual run costs at all.

1. Morning Briefing

Schedule: 7:00am weekdays, 8:00am weekends
Model: Opus

Pulls news on topics I care about: AI, Tesla (I work there), Texas BBQ, and marathon running. Compiles a digest and sends it to my phone via Telegram.

By the time I'm making coffee, I already know if anything relevant happened overnight.

This is the one job I run on Opus. It generates output I read every single day, and I want it sharp. The difference between an Opus briefing and a Sonnet briefing is noticeable: Opus surfaces connections between topics, catches nuance, writes tighter summaries.

2. Memory Maintenance

Schedule: 2:00am daily
Model: Sonnet

Reads all my conversations from the previous day. Extracts anything worth keeping into a dated notes file. Compresses older notes. Updates MEMORY.md if anything has changed significantly.

This job is the reason my memory system doesn't grow unbounded. Without it, MEMORY.md would eventually get large enough to eat a significant portion of my context window. This keeps it trim.

Sonnet handles this well. It's a read/extract/compress task, not creative generation.

3. Spanish Practice (3 crons)

Schedule: 8:00am, 1:00pm, 7:00pm daily
Model: Sonnet (+ ElevenLabs for the evening lesson)

Three separate crons throughout the day. Morning is vocabulary or grammar. Midday is conversational. Evening includes a voice component via ElevenLabs so I can hear pronunciation, not just read it.

The fact that these show up automatically is what makes the practice stick. When I had to opt-in, I'd skip. When it just appears on my phone, I do it.

I use a Spanish-trained ElevenLabs voice. English-trained voices sound wrong in Spanish (I made that mistake early on).

4. Family Event Reminders (3 crons)

Schedule: 7:00am, 12:00pm, 7:00pm daily
Model: Sonnet

Checks for upcoming family events and sends reminders at three points throughout the day. Three days before, the day before, and the morning of. My wife and I are in a shared group chat with the agent, so we both get the same reminders.

This turned out to be one of the most consistently valuable things my agent does. Fewer dropped-ball moments, fewer "I thought you told me" conversations.

5. Health Check

Schedule: 6:50am daily
Model: Sonnet

Checks that all other cron jobs ran successfully. If anything failed, sends me a Telegram notification immediately.

This is the most important job I have. Everything else depends on it.

Before I built this, I found out about failures when I noticed the morning briefing hadn't shown up. That could be twelve hours after the failure. Now I know within an hour.

6. Nightly Conversation Summary

Schedule: 11:00pm daily
Model: Sonnet

End-of-day review. Goes through all my conversations, extracts what matters, writes it to the daily notes file. This and the morning briefing are bookends. The briefing gets me oriented. The summary closes the loop.

7. AI Daily Digest

Schedule: 6:30am weekdays, 7:30am weekends
Model: Sonnet

Separate from the morning briefing. This one focuses specifically on AI news, new model releases, tool updates. Fires before the briefing so the briefing can reference anything important the digest surfaced.

Model Routing

I use two tiers: Opus for the morning briefing (where output quality matters most) and Sonnet for everything else.

If you're on the API and cost matters, there's a third tier. Models like Haiku can handle simple tasks (health checks, formatting, classification) for a fraction of the cost. I don't need it on a flat subscription, but it's a real option if you're watching per-token spend.

The routing principle is the same regardless of billing model: use the minimum capability that does the job well. If you're the head of a company and you send your principal engineer to grab coffee, you're misallocating. Sonnet handles the coffee runs. Opus is for the stuff that actually needs deep reasoning.

Common Failure Modes

The job runs but you can't tell. Add output delivery to every job. Telegram notification, file write, something you can inspect. If the only indication that a job ran is a log file you never check, you won't know when it's broken.

Timezone mismatch. This one got me. Some of my jobs were running in local time, some in UTC. That caused downstream failures because the expected input wasn't ready at the expected time. Be explicit about timezone in every cron config. TZ=America/Chicago at the top of your crontab.

Context going stale. The job still runs but produces worse output because MEMORY.md hasn't been updated in a week or the prompt references something that changed. The health-check cron catches outright failures. For quality drift, do a manual spot check periodically.

Rate limiting. If you have several cron jobs firing in close succession, you might hit API rate limits. I stagger my jobs by at least 15 minutes. The 7am briefing and 2am memory maintenance don't conflict because there's buffer.
